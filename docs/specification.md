# Specification: phases 1 to 4

The buildable spec for the phases built so far and the one in progress (see [ROADMAP.md](ROADMAP.md)). It
distills the long-form product spec into decisions an engineer can build from.
Where this file and the code disagree, fix one of them in the same commit.

Later phases get their own sections here when they're next.

## Ground rules (all phases)

1. **The database is the enforcement point.** Every person-facing read and write
   runs through `Tab.Repo.as_user/2`, which switches to the `tab_user` role so
   row-level security applies. Code outside `Tab.Accounts` never queries person
   data as the connection owner.
2. **Every table has RLS enabled and an explicit policy for each of select,
   insert, update, and delete**, written as SQL in its migration. One verb's
   policy never stands in for another's. `tab_user` has no DELETE privilege
   anywhere, so delete policies are written but no table grants delete.
3. **No hard deletes.** Removing something sets `deleted_at`. Soft-deleted rows
   drop out of balances and default views but stay in the audit log.
4. **Balances are computed, never stored.** No "settled" flags, no cached totals
   that clients can write.
5. **Nothing in the ledger needs AI, an API key, or the extraction service.**
6. **IDs are UUIDs** (`binary_id`), because `auth.uid()` returns a UUID.

## Decisions settled for these phases

| Question | Decision |
|---|---|
| Sign-in | `mix phx.gen.auth` with email magic links as the main way in (no password needed). Passwords optional for people who want one. Sessions are cookies. |
| Money | Whole cents in `bigint` columns named `*_cents`. One currency per instance, set by `TAB_CURRENCY` (default `USD`). No multi-currency. |
| Rounding | Shares are computed in cents. Each participant gets the floor of their exact share; the cents left over go one at a time to the participants with the largest fractional remainders, ties broken by participant order in the split. Shares always sum to the expense amount exactly. |
| Stored shares | When an expense is saved, its computed per-person amounts are written to `expense_shares`. The split definition is stored too, so the expense can be edited and re-split. |
| Categories | A `categories` table per group, seeded with Rent, Utilities, Internet, Groceries, Dining, Travel, Other. Groups can add and rename. |
| Who can pay an expense | A group member. Participants in a split can be members or external counterparties. |
| Per-category payments | A payment may carry a category. Category balances net only payments tagged with that category; untagged payments reduce the overall balance only. |
| Profiles vs. accounts | `users` (email, sign-in data) is visible only to its owner. `profiles` (display name, payment methods, reminder channel) is visible to anyone who shares an active group with that person. |
| Audit log | Written by Postgres triggers, not app code, so no code path can skip it. |
| Outbound mail | Resend through Swoosh's Resend adapter when `RESEND_API_KEY` is set (Cloud uses it, key in Doppler `tab/prd`). Generic SMTP (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`) for self-hosters who prefer it. With neither, mail goes to the server log, so a fresh install can still sign in, and the app warns at boot. Tab never runs a mail server for sending. Wired up in phase 2. |
| Leaving a group | You can't leave until you're even with everyone in it, including payments to you still waiting for your confirmation (`settle up before you leave`). An admin can remove anyone, even with money owed; their balances stay in the group. Payments with a former member count as soon as they're recorded (`self_attested`), since they can't confirm anything. Decided 2026-10-12. |
| Editing after payments | Allowed; balances recompute. The database stamps `expenses.edited_at` whenever what was spent, by whom, or how it's split changes, and the app shows the expense as edited. Everyone in the split gets an email when the amount or split changes (phase 2). Decided 2026-10-12. |
| Archiving a group | Admins archive any time (`groups.deleted_at`), with a warning first if anyone still owes money. An archived group is read-only for everyone, admins included, but stays readable and exportable. Admins can unarchive. Decided 2026-10-12. |
| Invites | Single-use and expiring (7 days by default), stored as a hash of the token, redeemed only through one database function that checks and consumes the invite atomically. |

## Phase 1: The ledger, enforced by the database

### Tables

All group-scoped tables carry `group_id` and `inserted_at`/`updated_at`. Ledger
tables (groups, invites, counterparties, categories, expenses) also carry
`created_by`, and payments carry `recorded_by`: a user id set from `auth.uid()`
by a `BEFORE INSERT` trigger, never trusted from the client. Most carry
`deleted_at`.

Ids are generated by the app (Ecto), so inserts don't use `RETURNING`. That
matters for groups: `RETURNING` would check the select policy before the
trigger has made the creator a member.

**users** (from `phx.gen.auth`, `--binary-id`): `id`, `email` (citext, unique),
`confirmed_at`, optional `hashed_password`, plus the generated `users_tokens`.

**profiles**: `user_id` (pk, fk users), `display_name`, `payment_methods` (jsonb
array of `{kind: venmo|zelle|cashapp|paypal|cash|check|other, handle: text}`),
`reminder_channel` (only `email` in v1). Made by a trigger on `users`, with the
email's local part as the starting display name.

**groups**: `id`, `name`, `created_by`, `deleted_at`.

**memberships**: `group_id`, `user_id`, `role` (`admin` | `member`), `joined_at`,
`left_at`. Unique active membership per `(group_id, user_id)`. The group's creator
gets an `admin` membership in the same transaction that creates the group.

**invites**: `id`, `group_id`, `token_hash`, `created_by`, `expires_at`,
`used_at`, `used_by`, `revoked_at`. The raw token appears once, in the link.
A trigger blanks `used_*` and `revoked_at` on insert and caps `expires_at` at
30 days; a revoked invite stays revoked.

**counterparties**: `id`, `group_id`, `name`, `contact_email` (optional), `notes`
(optional), `deleted_at`. A label for an outside party (a landlord, a utility, the
household next door). Not an account; can't sign in or see anything.

**categories**: `id`, `group_id`, `name`, `deleted_at`. Unique name per group.

**expenses**: `id`, `group_id`, `description`, `amount_cents` (> 0), `date` (the
day money left the payer's account), `category_id` (optional), `paid_by` (user id, a member),
`visibility` (`shared` | `private`), `split` (jsonb, the definition below),
`period_start`/`period_end` (optional, used from phase 3), `created_by`,
`deleted_at`.

**expense_shares**: `expense_id`, `group_id`, exactly one of `user_id` or
`counterparty_id`, `amount_cents` (>= 0). Written only by `set_expense_shares(expense_id, shares)`,
never directly by clients. A deferred constraint trigger checks at commit that
a live expense's shares add up to its amount and that a private expense has one
share, its creator's; `Tab.Ledger` forces the check early with
`SET CONSTRAINTS ... IMMEDIATE` so a bad split fails where it's written.

**payments**: `id`, `group_id`, `from_user_id` or `from_counterparty_id` (exactly
one), `to_user_id` or `to_counterparty_id` (exactly one), `amount_cents` (> 0),
`date`, `category_id` (optional), `method` (`venmo` | `zelle` | `cashapp` |
`paypal` | `cash` | `check` | `other`), `reference` (optional text, like a Venmo
note or check number), `status` (`pending` | `confirmed` | `self_attested` |
`declined`), `recorded_by`, `confirmed_at`, `confirmed_by`, `deleted_at`.

**audit_log**: `id`, `group_id`, `table_name`, `row_id`, `action` (`insert` |
`update` | `soft_delete`), `actor_id` (from `auth.uid()`), `before` and `after`
(jsonb), `private_owner_id` (set when the row is or was a private expense),
`at`. Audited tables: groups, memberships, invites (without `token_hash`),
counterparties, categories, expenses, payments. Shares aren't audited on their
own; the expense's `split` records them. Triggers refuse UPDATE, DELETE, and
TRUNCATE on the log for every role, the owner included.

### Splits

The `split` jsonb holds one of these, as
`{"type": ..., "entries": [{"user_id" | "counterparty_id": ..., "value": ...}]}`
(`tiered` adds `"rest": <split>`). `Tab.Ledger.Split` computes them to cents
with the rounding rule above; the shares are written to `expense_shares`.

| Type | Definition | Example |
|---|---|---|
| `equal` | participants | $90 among A, B, C: 30/30/30 |
| `exact` | participant → cents; must sum to the amount | A $50, B $40 |
| `percentage` | participant → percent; must sum to 100 | 60/40 |
| `shares` | participant → positive integer weight | 2:1:1 |
| `tiered` | a list of fixed allocations (participant → cents) taken off the top, then any of the four above for the remainder | $70 to A first, then 60/40 of the rest |

`tiered` is the only compound type. It does not nest, and there is no general
formula language.

### Payment status rules (enforced in the database)

- When both sides are different members who have accounts, a new payment is
  `pending`. Only the **payee** can move it to `confirmed` or `declined`, and
  that decision is final. `confirmed_by` records who decided.
- When the payee records the payment themselves, it's `confirmed` as written:
  the person it benefits is the payer, so there's nothing to confirm.
- Changing a payment's amount, date, or parties sets its status again from
  these rules (so a confirmed payment goes back to `pending`). Only whoever
  recorded it may edit it.
- When either side is a counterparty, a new payment is `self_attested` and counts
  immediately. The same applies in a group with one member.
- Nobody can set `confirmed` or `self_attested` directly on insert in a way that
  breaks the rules above: a `BEFORE INSERT` trigger sets `status` from the parties.
- `declined` and soft-deleted payments never count toward balances.

### Balances

A security-invoker view, `balances`, returns one row per `(group_id, debtor,
creditor)` pair, where each side is a member or a counterparty:

```
owed  = sum(expense_shares where the debtor is the participant and the creditor paid,
            excluding the payer's own share and soft-deleted expenses)
paid  = sum(payments from debtor to creditor with status confirmed or self_attested)
net   = owed - paid   (pairs are netted in both directions; only the positive side is shown)
```

`category_balances` is the same, grouped by category, netting only payments
tagged with that category. Because both views use `security_invoker`, a person
sees exactly the rows their own policies allow. Private expenses never produce
shares owed to anyone else, so they never enter group balances.

Settle-up suggestions are computed in Elixir from `balances`, read-only: match
the largest debtor with the largest creditor until everyone's even, which takes
at most one fewer payment than there are people with a balance. They suggest
payments; they don't record any.

### Row-level security, table by table

Reads use `auth.is_member(group_id)`. Writes use `auth.can_write(group_id)` and
`auth.can_admin(group_id)`, which also require the group not to be archived;
wherever the table below says "members" or "admins" for insert or update, read
it that way. `auth.is_member(group_id)` and `auth.is_admin(group_id)` are `SECURITY DEFINER`,
`STABLE` SQL functions over active memberships, so policies on `memberships`
itself don't recurse.

| Table | select | insert | update | delete |
|---|---|---|---|---|
| users | own row | none (sign-up runs as owner in `Tab.Accounts`) | none (account changes run as owner) | none |
| users_tokens | none | none | none | none |
| profiles | own row, or anyone sharing an active group | none (made by a trigger with the user) | own row | none |
| groups | members | any signed-in user (creator becomes admin) | admins | none |
| memberships | members of that group, and your own rows after you leave | none directly (group creation and `accept_invite` only) | admins (role, `left_at`); a member may set their own `left_at` | none |
| invites | admins of that group | admins | admins (revoke only) | none |
| counterparties | members | members | members | none |
| categories | members | members | members | none |
| expenses | shared: members; private: only `created_by` | members, with `created_by = auth.uid()`; private ones must have the creator as payer and only participant | the creator, or an admin for shared expenses | none |
| expense_shares | follows its expense | none directly (expense functions only) | none directly | none |
| payments | members | members, as `recorded_by` | payee (confirm/decline a pending payment); recorder (edit details, soft-delete) | none |
| audit_log | members, except entries with a `private_owner_id` other than the viewer | none (triggers only) | none | none |

UPDATE grants are column lists, so nobody can move a row to another group or
change who created it. Internal tables (`schema_migrations`, `oban_*`,
`users_tokens`) grant `tab_user` nothing.

Two functions people call directly are `SECURITY DEFINER`, because the rows
they write have no direct-write policy:

- `accept_invite(token)` can't know the group until the token is checked. It
  validates the token hash, expiry, revocation, use, and archived group, then
  marks the invite used and inserts the membership. Every invalid case raises
  the same error (hint `invalid_invite`), so a guess learns nothing. Someone
  already in the group gets `already_member` and the invite isn't used up.
- `set_expense_shares(expense_id, shares)` checks the caller could edit the
  expense under the `expenses` update policy, then replaces its shares and
  checks everyone in the split is or was in the group.

Triggers and policies use `SECURITY DEFINER` helpers in `auth` and `ledger`
schemas, each with a pinned `search_path`.

### Elixir side

- Contexts: `Tab.Accounts` (sign-in; runs as owner), `Tab.Groups`
  (groups, memberships, invites, counterparties, categories), `Tab.Ledger`
  (expenses, splits, payments, balances, settle-up suggestions).
- Every public function in `Tab.Groups` and `Tab.Ledger` takes the current user
  (a `%Tab.Accounts.Scope{}`) and runs inside `Repo.as_user/2`.
- Split math lives in a pure module, `Tab.Ledger.Split`, with no database access.

### Tests that must pass before phase 2

1. **The policy matrix.** For every table and every verb, a test runs the action
   as each of: a member, an admin, a non-member, the private-expense owner, and
   another member, and checks it's allowed or refused as the table above says.
   These run raw SQL through `Repo.as_user/2`, not through the contexts, to prove
   the database refuses on its own.
2. **Split math (property tests with StreamData):** shares always sum to the
   amount; no share is negative; `equal` shares differ by at most one cent;
   `tiered` gives the fixed amounts first and splits the rest correctly.
3. **Balances match hand arithmetic** on fixed scenarios: Priya's four-person
   house, Marcus alone with counterparties only, two partial payments against
   one balance, a declined payment that doesn't count, and a soft-deleted
   expense that drops out.
4. **Private expenses** are invisible to every other member, including the group
   creator, in `expenses`, `expense_shares`, `balances`, and `audit_log`.
5. **Invites** work once, fail after expiry, revocation, or use, and can't be
   accepted for a group by guessing.
6. **Audit:** every insert, update, and soft delete on ledger tables writes
   exactly one audit row with the right actor; no role used by the app can
   delete or change audit rows.
7. **Payments:** a member-to-member payment starts pending and only the payee can
   confirm it; a counterparty payment and a solo user's payment are
   self-attested immediately and show as such.
8. **No hard deletes:** `tab_user` lacks DELETE on every table (one test walks
   `information_schema`).

These cover the phase-1 items in the long-form spec's acceptance criteria (§9):
group create/invite/join, the single-member group, equal and exact splits,
server-computed balances, two-party confirmation, self-attested payments, audit
on every change, private-expense invisibility, payments vs. expenses in balances,
per-category balances, tiered splits, counterparties, partial payments, and the
direct-bypass checks.

## Phase 2: The web app people use

LiveView pages on the b28 clay kit (`web/assets/vendor/b28-clay.css`). Phoenix's
default daisyUI is removed in this phase and `core_components.ex` restyled on the
kit, so the app and the website read as one family. Every page works at 360 px
wide with no sideways scrolling. Copy follows the brand voice and `stop-slop`.

### Pages

| Page | What you can do |
|---|---|
| Sign in | One email field: Tab emails a link that works once, for 15 minutes. A new email gets an account made on the spot, and the reply is the same either way, so the page never reveals who has an account. The first sign-in asks for a display name (`/welcome`), then continues to wherever the person was headed, such as an invite link. A password is optional, under Email and password. |
| Your groups | See your groups with your net balance in each; create a group. |
| Group | Balances (who owes whom, overall and by category), recent activity, pending payments waiting on you. |
| Add expense | Description, amount, date (defaults to today), category, who paid, who's in, and the split type. Shows each person's share live before saving. Can be marked private. |
| Expense | Details, the computed shares, edit, delete (soft), and its history from the audit log. |
| Settle up | Suggested transfers; record a payment with method and reference. Pending payments show as waiting; the payee sees Confirm and Decline. |
| Members and invites | Admins create, copy, and revoke invite links; see members; add counterparties. |
| Join | Opening an invite link signs you in if needed, then joins the group. Used, expired, and revoked links say so plainly. |
| Profile | Display name and payment methods (shown to people you share a group with). |
| Export | `GET /export.csv`: every expense you paid for or have a share in (private ones and deleted ones included, marked), and every payment to or from you, across all your groups, read as you. Cells starting with `=`, `+`, `-`, or `@` are prefixed so spreadsheets don't run them. |

### Email notifications

- Sent by Swoosh from an Oban job (queue `mail`), so a slow or failing mail
  service never blocks a page. Jobs are enqueued after the ledger write commits,
  as the connection owner, because people's own role can't touch the job table.
- The job builds the email as its recipient, through `Repo.as_user/2`, so an
  email can only contain what that person is allowed to see. Someone who has
  left by the time the job runs gets nothing.
- Three events: a new shared expense you're part of, a change to the amount or
  split of one you're part of, and a pending payment waiting for you to confirm.
- One email per event, to the people involved, never to the person who caused it.
- Sent through Resend or SMTP (see "Outbound mail" above). With neither set,
  notifications are skipped and logged, sign-in links go to the log, and
  everything else works.

### Tests that must pass before phase 3

1. LiveView tests for each page's main path and its refusals (a non-member opening
   a group URL gets a 404, not an error page that leaks the group's name).
2. The full journey in one test: sign up, create a group, invite, join, add an
   expense of each split type, see balances, record a partial payment, confirm
   it, see the balance drop, export CSV.
3. A solo user's journey with only counterparties, with no invite ever sent.
4. Notifications enqueue the right emails, and the app works with no mail
   settings at all.
5. No hard-coded colors outside the clay kit tokens (`test/tab_web/clay_tokens_test.exs`;
   Tailwind's default palette is also switched off in `app.css`), and every page
   fits 360 px with no sideways scrolling (`mise run check:narrow`, a CI job:
   headless Chrome loads each page in a 360 px frame via the dev-only `/dev/narrow`).

These cover the phase-2 items in the long-form spec's acceptance criteria:
payment methods visible to group-mates, a payment storing its method and
reference, the reminder email, and unlimited expenses and full export with no
caps on any plan.

## Phase 3: Recurring bills and household tools

Bills that come every month, people who go away for a while, and chasing money
without awkward texts. Everything here builds on the phase 1 ledger: a logged bill
is a normal expense, a suggestion is only a suggestion until someone saves it, and
nothing here needs AI.

### Decisions for this phase

| Question | Decision |
|---|---|
| A bill's normal split | The recurring template's `default_split` when the bill comes from a template; otherwise an even split among current members, as in phase 2. Categories don't carry splits of their own. Decided 2026-10-12. |
| Overlapping temporary splits | The database refuses two live overrides whose dates overlap on the same bills (an override with no category covers every category). Adding one that overlaps shows the clash and a combined suggestion for the shared days; when the admin confirms, Tab saves non-overlapping date ranges, so each day of each category has at most one override. Decided 2026-10-12. |
| Matching payments to bills for float | Oldest first. Payments between two people pay off the oldest unpaid shares between them first, and a share owed the other way counts as repayment on its own date. Decided 2026-10-12. |
| Statement links | Any member can make one for anyone in the group, member or outside party. It covers one calendar month, shows only that person's own charges and payments, never private expenses, works for 30 days, and anyone in the group can revoke it. Decided 2026-10-12. |
| Override split types | `equal`, `percentage`, or `shares`: the types that don't depend on the amount, since an override covers bills not yet known. Templates may also use `exact` (rent split as fixed dollar amounts). Neither stores `tiered`; a tiered bill is still one edit away in the expense form. |
| A prorated suggestion | Saved as a `shares` split with whole-number weights, reduced to lowest terms. It reproduces the blended amounts and still re-splits sensibly if someone edits the total. No new split type. |

### Tables

**recurring_templates**: `id`, `group_id`, `name` (unique per group among live
templates), `category_id` (optional), `cadence` (`monthly` | `bimonthly` |
`quarterly` | `custom_n_days` | `irregular`), `cadence_days` (required for
`custom_n_days`, 1 to 366, otherwise null), `stability` (`fixed` | `variable`),
`default_payer` (optional, a user who is or was a member), `default_split`
(optional jsonb; `equal`, `exact`, `percentage`, or `shares`), `autopay_day`
(optional, 1 to 31), `last_amount_cents` and `last_logged_on` (set by the
database, never by people), `created_by`, `deleted_at`. The long-form spec lists
`custom_n_days`; `quarterly` is added because "every 91 days" drifts.

**expenses** gains `template_id` (optional, same group, shared expenses only).
A trigger keeps the template's `last_amount_cents` and `last_logged_on` equal to
its newest live expense, on insert, edit, and soft delete.

**split_overrides**: `id`, `group_id`, `category_id` (null means every
category), `effective_from`, `effective_until` (optional; null means until
someone ends it), `split` (jsonb, see the decision above), `note` (like "Alex
away"), `created_by`, `deleted_at`. A trigger refuses overlap with another live
override in the same group whose categories collide (hint `override_overlap`),
holding a per-group advisory lock so two admins can't race past it.

**statement_links**: `id`, `group_id`, `token_hash`, exactly one of `user_id`
(a user who is or was a member) or `counterparty_id`, `period_start` (first of a
month), `period_end` (last day of that month), `expires_at` (30 days out, capped
there by a trigger), `revoked_at`, `created_by`. The raw token appears once, in
the link. A revoked link stays revoked.

All three new tables are audited (`statement_links` without `token_hash`) and
stamped (`created_by` from `auth.uid()`).

### Row-level security for the new tables

| Table | select | insert | update | delete |
|---|---|---|---|---|
| recurring_templates | members | members | members (all fields people set, and `deleted_at`) | none |
| split_overrides | members | admins | admins (dates, category, split, note, `deleted_at`) | none |
| statement_links | members | members | members (`revoked_at` only) | none |

Reading a statement takes no sign-in: `read_statement(token)` is `SECURITY
DEFINER` and returns one JSON document. It checks the token hash, expiry, and
revocation, and every failure raises the same error (hint `invalid_statement`).
The app calls it as `tab_user` with no person set (`Tab.Repo.as_nobody/1`), so
the caller can't read any table directly. The document holds the group's name,
the recipient's name, the month, that month's shared expenses with a share for
the recipient (date, description, total, their share, who paid), payments to or
from them that month (counted ones and waiting ones, marked), and where they
stand today with each person they owe or who owes them.

### Recurring templates and one-tap logging

- The **Bills** page lists a group's templates: name, how often, about how much
  (`last_amount_cents`), when last logged, and a **Log it** button. Members add,
  edit, and remove templates there.
- **Log it** opens the add-expense form filled in from the template:
  description from the name, amount from `last_amount_cents`, category, payer
  (`default_payer`, else you), split (see "Which split the form suggests"), date,
  and the period the bill covers. Saving goes through `Tab.Ledger.create_expense`
  like any expense: same policies, same audit log, with `template_id` set.
- **Date:** with `autopay_day`, the latest occurrence of that day on or before
  today, with day 31 (or 29, 30) clamped to the month's last day. Without it,
  today. Always editable.
- **Period:** ends the day before the date and reaches back one cadence: a
  monthly bill dated Oct 3 covers Sep 3 to Oct 2. `irregular` leaves the period
  empty. Always editable; the form shows "Bill covers" dates for every expense.
- **Stability:** for a `fixed` template, an amount different from
  `last_amount_cents` shows "Rent is usually $1,000.00" and Save needs a ticked
  "Yes, the amount changed" box. A `variable` template asks nothing.

### Temporary splits (time-bound overrides)

- The **Temporary splits** page lists the group's overrides, current and coming
  first. Admins add, edit, end, and remove them; members read them.
- **Someone's away** is the quick way in: pick the person, the dates, and the
  category (or all). Tab proposes the split without them: the template's
  default split for that category with their share spread over the others by
  their existing ratios, or an even split among the other current members. The
  admin reviews and saves it.
- An override applies only to expenses dated inside its window. After
  `effective_until`, new expenses fall back to the normal split with no action.
- **Combining overlaps:** saving an override that overlaps live ones shows each
  clash and a combined suggestion for the shared days: each person's weight is
  their fraction under one override times their fraction under the other, so
  someone left out of either stays out. Confirming trims and splits the
  existing rows and inserts the pieces in one transaction. If nobody is left in
  both, there's no suggestion, and the admin writes the split for those days.
  Combining needs both to cover the same bills: when one covers every category
  and the other one category, the page says so and the admin changes one first.
  Editing an existing override into an overlap gets no combined suggestion,
  only the clash.

### Which split the form suggests

When adding an expense, until the person edits the split fields, the form
suggests a split from the template (if any), the category, the date, and the
period, and says why ("Alex is away for 12 of this bill's 30 days").

1. Start from the normal split (the decision above).
2. With no period: if an override covers the expense's date and category, use
   its split in place of the normal one.
3. With a period of `D` days: each override covering `d_k` of those days
   (respecting category) weighs in for its days, and the normal split for the
   remaining `D - Σ d_k`. Each person's weight is the sum over those pieces of
   (their fraction of the bill under that piece's split) × (its days). An
   `exact` normal split counts as fractions of this bill's amount. The result is
   a `shares` split; people at zero drop out.

Each bill is prorated against its own period, so an absence spanning two bills
gives two separate fractions with no change to the stored override. This is
day-based proration, the way a landlord prorates a mid-month move-out, not
metering; the page never calls it usage. Editing an existing expense keeps its
saved split.

### Float: how long money waits

`Tab.Ledger.Float` (pure Elixir) works from the expenses, shares, and payments
the viewer can already see. No new table and no new visibility rule.

- For each pair of parties, walk the money between them by date (expenses
  before payments on the same day). A share opens a lot from the person who owes
  to the person who paid. A payment, or a share owed the other way, closes the
  oldest open lots first; anything left over opens a lot the other way.
- A share's days are its repayment date minus the expense date (at least 0),
  weighted by cents when it closes in parts; an open share counts up to today.
- The group page shows, for each member who has paid for others, the average
  days their money waits (weighted by cents). The expense page shows each share
  as "paid back after 9 days" or "unpaid for 14 days".
- Days only. No interest rate, no dollar cost of waiting.

### Reminder drafts

`Tab.Reminders` (pure Elixir string templates, no AI, no network) drafts three
messages from one balance: a Venmo note (one line), a text (two or three
sentences), and an email (subject and body). Each says how much, for what (the
oldest open bills from the float walk, up to three, then "and N more"), and how
to pay you (your payment methods). Tab never sends them; you copy one and send
it from your own app.

The **Ask for it** page (`/groups/:id/remind/:party`, linked from every "owes
you" line) shows the three drafts with Copy buttons. **Add a statement link**
makes a link for that person for a month you pick (this month by default) and
puts it in the drafts. The page also lists that person's live links, with
Revoke.

### Statement page

`/s/:token`, no sign-in, outside the signed-in pages, sent with
`cache-control: no-store`, `referrer-policy: no-referrer`, and
`x-robots-tag: noindex`, since the token is in the URL: the month's activity for
one person, as `read_statement` returns it, on the clay kit, at 360 px. An
expired, revoked, or unknown link shows one plain "This link doesn't work
anymore" page with a 404, whichever it was.

### Tests that must pass before phase 4

1. **Policy matrix** for `recurring_templates`, `split_overrides`, and
   `statement_links`, every verb, as member, admin, and non-member, in raw SQL.
2. **Statement links, straight against the database:** a link shows only its
   recipient's slice of its own month; private expenses never appear; expired,
   revoked, and made-up tokens fail alike; with no person set, every table
   refuses reads.
3. **Templates:** made by hand, logged with one tap at `last_amount_cents`,
   producing an audited expense with `template_id`; `last_*` follows edits and
   deletes; `fixed` asks for confirmation on a changed amount, `variable`
   doesn't; `autopay_day` sets the date, clamped at month end, and stays editable.
4. **Overrides:** "Alex away from utilities, Nov 1 to 30" applies to utilities
   bills dated inside, never touches rent, and stops on its own after Nov 30;
   overlaps are refused by the database and the combine flow saves the right
   pieces; a 48-day absence over two monthly bills gives each bill its own
   fraction (property tests: suggested shares always add up; zero days gives the
   normal split; full overlap gives the override's).
5. **Float:** a share paid back 9 days later shows 9; an unpaid share counts up
   with today; partial payments, offsets, and overpayment follow oldest first.
   **Drafts:** Venmo, text, and email render from the same balance.

These cover the phase-3 items in the long-form spec's acceptance criteria (§9):
recurring templates and one-tap logging, fixed versus variable stability,
`autopay_day` dates, float, reminder drafts without AI, scoped statement links
tested at the database, time-bound overrides with automatic reversion,
overlap flagged rather than combined in silence, and per-bill proration.

## Phase 4: Reading bills

Send Tab a bill and it fills in the expense for you to check. A photo of a
receipt, a PDF, or a forwarded email turns into a pending item with the amount,
the date, the dates it covers, and a suggested split. Nothing reaches the ledger
until the person confirms it. Every part of the ledger keeps working with the
reader switched off.

### Decisions for this phase

| Question | Decision |
|---|---|
| Receiving mail on self-host | Resend inbound. The self-hoster points a domain's MX at Resend (or uses their account's `<id>.resend.app` address), and Resend posts an `email.received` webhook to Tab. Tab never runs a mail server, so no port 25, no MX on the Tab server, no spam filtering of its own. Cloud uses the same path until the Cloudflare relay arrives with the Cloud edition (phase 6). Replaces the long-form spec's `gen_smtp` listener. Decided 2026-10-13. |
| Whose key reads bills | One Anthropic key for the whole server, `ANTHROPIC_API_KEY`, set on the `extract` service only (Doppler or `.env`). The web app never holds it. Model: Claude Haiku 5.5 (`claude-haiku-5-5`), fixed, not a setting. Per-person keys wait for Cloud. Decided 2026-10-13. |
| What phase 4 covers | Photo and PDF upload, forwarded email with a setup guide, the review list, matching bills to phase 3 templates, and the digest. Submission links for people without an account wait for the Cloud edition, since their cost lands on the issuer's allowance. Decided 2026-10-13. |
| The original document | Deleted once its bill is saved or dropped, always: Tab doesn't store bills' sensitive originals. What stays with the expense is a reference anyone who can see the expense can read: what it was, who sent it, the subject, the date, the amount, and a search line (Gmail's syntax, readable anywhere) for finding it in the mailbox it came from. | One bill, several documents | A pending item is one bill and holds every document about it: the statement, a "bill is ready" email, autopay scheduled, payment made, a reminder. | Forwarded by hand | The sender, subject, and date come from the forwarded block (Gmail, Apple Mail, Outlook), not the forwarder's headers. The same email forwarded twice is caught by sender, subject, and date, since its bytes differ. |
| A balance carried from earlier bills | The form fills in this period's charges only (`period_cents`: the printed current charges, else total minus the carried balance), so a bill already logged never counts twice. Decided 2026-10-13. |
| A past-due bill | Flagged "Past due" in Bills to check, on the bill, and on the form, with a note to check autopay. No extra email. Decided 2026-10-13. |
| Late bills | A regular bill (not `irregular`) shows "Late" on the Bills page when nothing has been logged a week past one cadence after the last one, and the digest lists it for whoever usually pays it, or everyone in the group when nobody's set. Needs no reading. Decided 2026-10-13. |

| Photos | Resized in the browser to at most 1600 px on the long side and re-encoded as JPEG before upload, so phone photos (including HEIC, which the model can't take) arrive small and in a format it reads. |

### Configuration

| Variable | Service | Meaning |
|---|---|---|
| `ANTHROPIC_API_KEY` | extract | Turns bill reading on. Without it, uploads and mail still land as pending items with the original attached and the fields blank, for typing in by hand. |
| `RESEND_API_KEY` | web | Already used for sending; also fetches received mail. |
| `RESEND_WEBHOOK_SECRET` | web | The `email.received` webhook's signing secret. Without it, the inbound endpoint answers 404 and the forwarding section says mail isn't set up on this server. |

### Tables

**forwarding_addresses**: `id`, `user_id`, `group_id`, `local_part`
(unique), `created_at`, `revoked_at`. One live address per person per group
they're in, like `elm-street-house-k3x9m2ab4q@bills.tab.b28.dev`: the group's
name so people can tell their addresses apart, then a random 10-letter tag,
the only secret. Mail to it lands in that person's Bills to check, already
set to that group. Making a new one revokes the old one for that group. Mail
to the address of a group the person has left goes nowhere. Decided
2026-10-13 (one per person per group, over one shared per group and one per
person).

**inbound_messages**: `id`, `provider` (`resend`), `provider_id` (unique, so a
retried webhook lands once), `user_id` (null until matched), `status`
(`fetching` | `stored` | `unmatched` | `failed`), `received_at`, `from_address`,
`subject`. Written as the connection owner by the webhook handler, never by a
person; the owner can read their own.

**documents**: `id`, `user_id`, `item_id` (the bill it's about; it moves when
bills join), `kind` (`photo` | `pdf` | `email`), `content_type`, `filename`,
`byte_size`, `sha256`, `fingerprint` (sender, subject, and date of an email),
`content` (`bytea`, null once purged), `role` (`bill` | `notice` |
`autopay_scheduled` | `payment` | `reminder` | `other`), `sender`, `subject`,
`sent_at`, `amount_cents`, `search`, `expense_id` (the expense it's a
reference for), `purged_at`, `created_at`. Size caps: 10
MB for a PDF or a raw email, 2 MB for a photo after the browser resizes it.

**pending_items**: `id`, `user_id`, `source` (`upload` | `email`), `status`
(`reading` | `ready` | `unreadable` | `waiting` | `confirmed` | `dismissed` |
`merged`, for an item whose document joined another bill or a saved expense), `doc_type` (see below), `proposal` (jsonb, what the
reader returned, validated), `due_on`, `template_id` (a suggested match),
`group_id` (suggested), `expense_id` (set on confirm), `duplicate_of` (a likely
duplicate expense, for the warning), `read_at`, `created_at`.

**recurring_templates** gains `sender` (optional, lowercase domain or address,
like `pge.com`), set when someone confirms a bill from that sender against the
template.

**profiles** gains `digest_days` (int array, default `{10,25}`, each 1 to 28).

These tables belong to one person, not a group, so they stay out of the
group audit log (which is per group). Each keeps its own trail in its
columns (`read_at`, `status`, `purged_at`), and the expense an item becomes
is audited like any other.

### Row-level security for the new tables

| Table | select | insert | update | delete |
|---|---|---|---|---|
| forwarding_addresses | owner | owner, for a group they're in | owner (`revoked_at` only) | none |
| inbound_messages | owner | none (webhook only) | none | none |
| documents | owner; members of the expense's group once it's a reference for an expense | owner, on their own item | owner (`item_id` to their own item, `expense_id`, `role`, `amount_cents`, `search`, purge: `content` to null with `purged_at`) | none |
| pending_items | owner | owner | owner | none |

Purging sets `content` to null; the row stays for the audit trail. A trigger
refuses setting `content` back once purged, and refuses `expense_id` on an
expense the owner can't see or a private one that isn't theirs.

### The reader (`extract/`)

- One endpoint, `POST /read`, takes JSON: `kind` (`photo` | `pdf` | `email`),
  base64 content and type, and for email the subject, sender, and text body. It
  returns the type and the fields below, or an error. No database, no tools, no
  memory between calls.
- One BAML call per document on Claude Haiku 5.5 returns the type and the
  fields together (one call costs half of classify-then-extract, and the type
  rides along fine). Types: `utility`, `receipt`, `subscription`, `rent`,
  `travel`, `phone`, `other`. Amounts come back as printed and BAML code turns
  them into cents.
- Fields: `merchant`, `total_cents`, `current_cents` (this period only),
  `previous_cents` (carried from earlier bills), `past_due`, `date`, `due_on`,
  `period_start`, `period_end` (with several service periods, the earliest
  start and latest end), `account_hint` (last 4 only), `line_items` (description, cents),
  `tax_cents`, `tip_cents`, and `confidence` per field. A field the reader isn't
  sure of comes back null; the app never fills a guess.
- The app validates everything it gets back: amounts positive and under $1
  million, dates within two years, line items adding up to the total within a
  dollar (else line items are dropped). Anything that fails is blank on the form.
- Text inside a document can't do anything but change the proposal. The reader
  has no way to act, and the person confirms every field.

### Getting documents in

- **Upload** (`/inbox`, "Add a bill"): a photo or PDF, several at once. Each
  becomes a `documents` row and a pending item in `reading`, then an Oban job
  calls the reader.
- **Forwarded email:** Resend posts `email.received` to `POST /inbound/resend`.
  Tab checks the Svix signature (`svix-id`, `svix-timestamp`, `svix-signature`,
  HMAC-SHA256 over the raw body, five-minute tolerance), writes an
  `inbound_messages` row keyed by Resend's email id, and only then answers 200.
  A bad signature gets 401; a database failure gets 503, so Resend retries (for
  about 27 hours). An Oban job fetches the message
  (`GET /emails/receiving/{id}`, then its signed raw download), matches a live
  forwarding address among the recipients, stores the raw message as a
  `documents` row, and makes the pending item. Mail to an unknown or revoked
  address is marked `unmatched` and dropped without a reply.
- **Which part of an email gets read:** the first PDF attachment if there is
  one, else the first image, else the text body (HTML stripped). The subject
  and sender go along either way.
- **Gmail's forwarding check:** turning on auto-forward makes Gmail send a
  confirmation code to the new address. Tab spots it (from
  `forwarding-noreply@google.com`), skips reading, and shows the code on the
  forwarding page.
- **Duplicates:** a document with the same `sha256` as one the person sent in
  the last 90 days is turned away: an upload says so, and an email shows as
  "already here" on the forwarding page. After reading, an expense in their
  groups with the same amount within 5 days of the same date sets
  `duplicate_of`, and review warns before saving.
- **The daily limit:** past `TAB_READS_PER_DAY`, items wait in `waiting` and a
  job reads them the next day.
- **Out of API credit:** when Anthropic answers "credit balance is too low",
  the reader answers 503 `paused`, and the item waits like the daily limit,
  tried again the next day. Nothing is charged.

### Review

- `/inbox` lists the person's pending items, newest first: what it is, the
  amount, the due date, and a time-sensitive flag when `due_on` falls before
  their next digest day. A chip on the groups page shows how many are ready.
- Opening one shows the original (image, PDF, or email text) beside the
  add-expense form, filled in from the proposal: description from the merchant,
  amount, date, the period the bill covers, category from the type, and the
  group and split from the matched template. Everything is editable and goes
  through `Tab.Ledger.create_expense`, the same as typing it in.
- **Matching a template:** the sender's domain or address against
  `recurring_templates.sender` in the person's groups, else the merchant name
  against template names. A match prefills like **Log it** (phase 3: split,
  payer, autopay date, fixed-amount check) and says so: "Looks like your
  Electric bill, split like last time." A first bill from a sender with no
  match offers a "Treat bills from pge.com as a bill" box on the form; ticked,
  saving also makes a template from the expense, with the sender.
- **Receipts with line items:** the review page lists them beside the
  original. To give an item to one person, use the form's "Fixed amounts
  first, then the rest" split (`tiered`).
- **Unreadable** items, and every item when the reader is off, open the same
  form with blank fields and the original beside it.
- Dismissing or confirming an item purges its documents' content. Confirming
  turns them into references on the expense, shown as "What arrived about this
  bill" with a Copy search button.

### The digest

- Items arrive and get read right away, with no email each. On each of a
  person's `digest_days`, at 9:00 server time, one email lists their ready
  items, if any.
- An item due before the next digest day doesn't wait: it gets its own email
  when it's read, saying when it's due.
- People pick their digest days on the You page: the 10th and 25th (the
  default), the 1st and 15th, the 1st, or "as each bill arrives" (no digest
  days: each bill gets its own email once read).

### Forwarding setup

`/inbox/forwarding` shows the person's address with a Copy button, a button to
make a new one, and steps for setting up a filter that forwards a sender's
bills, for Gmail, Outlook.com, iCloud Mail, and Fastmail. Tab never asks for
access to anyone's mailbox. The page shows the last few emails received, so
people can see the filter worked.

### Tests that must pass before phase 5

1. **Policy matrix** for the four new tables, every verb, as owner, other group
   member, and stranger, in raw SQL; a kept document is readable by the
   expense's group and nobody else; a purged document can't be refilled.
2. **The review gate:** no reader output, upload, or email creates an expense
   without a person confirming; a reader reply full of instructions only ever
   lands as field values. Tested with a scripted reader, no network.
3. **Mail:** a correctly signed webhook lands once, even sent twice; a bad
   signature gets 401 and nothing written; a database failure gets 503; mail to
   an unknown or revoked address writes no pending item; a forwarded utility
   bill is classified `utility`, and a second bill from the same sender
   prefills last time's split.
4. **The digest:** two bills forwarded on the 3rd and 7th with digest days
   `[10, 25]` are read on arrival, send no email each, and appear together in
   one digest on the 10th; one due on the 8th gets its own email.
5. **Reader off:** with no `ANTHROPIC_API_KEY` and `extract` stopped, uploads
   and mail still land as items to fill in by hand, and `/healthz` stays 200.
   BAML tests cover classification and parsing against recorded replies.

These cover the phase-4 items in the long-form spec's acceptance criteria (§9):
photo upload to confirmed expense, forwarded utility bills classified and
prefilled from last time, the forwarding guide without mailbox access, the
digest and the time-sensitive flag, and the autopay date on confirm.
